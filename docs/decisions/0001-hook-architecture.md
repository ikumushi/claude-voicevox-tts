# 0001. 読み上げを Hook + 切り離しワーカーで実装する

- 日付: 2026-10-03
- 状態: 採用

## 背景

Claude Code の応答を VOICEVOX で読み上げたい。読み上げのために作業が止まったり遅くなったりするのは
本末転倒なので、「応答が終わった瞬間から体感の遅延を増やさない」ことを最優先にした。

## 検討した案

1. **Stop Hook の中で合成も再生も済ませる**
   実装は一番素直。ただし音声合成に数百ミリ秒〜数秒、再生にはテキストの長さぶんの時間がかかる。
   Hook が終わるまでターンが閉じないため、毎回待たされる。却下。
2. **常駐サーバを立て、Hook から読み上げ依頼を投げる**
   遅延は出ないが、サーバの起動・停止・死活監視を自分で面倒みることになる。
   読み上げ1機能に対して仕掛けが大きすぎる。却下。
3. **Hook は読み上げ文を決めてワーカーを切り離し、すぐ終わる**(採用)
   Hook 本体の仕事はトランスクリプトの読み出しとテキスト整形だけなので数十ミリ秒で終わる。
   合成と再生は `detached: true` で切り離した子プロセスが引き受ける。常駐プロセスは不要。

## 決定

案3を採用する。

- `speak-hook.mjs` … 読み上げ文を決め、一時ファイルに書き、`speak.mjs` を切り離して起動して終了する
- `speak.mjs` … エンジンの起動確認・音声合成・再生を担当する

新しいターンの読み上げが始まったら古い読み上げは止めたいので、ワーカーは自分のプロセスIDを
一時ファイルに記録し、次のワーカーが `taskkill /T` でそのプロセスツリーを落とす。
Windows では親プロセスを落としても子(再生用の PowerShell)が残るため `/T` が必要。

## 結果

- ターンの終わりに体感の遅延は出ない
- 常駐プロセスの管理が不要
- 読み上げが失敗しても Hook は終了コード0で黙って終わるので、作業は止まらない
- 代償として、読み上げの失敗はその場では気づきにくい。確認用に `npm run status` を用意した

## 関連する決定: TypeScript を使わない

ワークスペース標準は TypeScript だが、このプロジェクトは素の ESM(`.mjs`)で書く。
Hook は Claude Code から `node <ファイル>` で直接起動されるため、ビルド成果物を挟むと
「コードを直したのに古い `dist/` が動く」事故が起きる。ビルド工程を持たないほうが安全。
型が欲しい箇所は JSDoc で補い、振る舞いは Vitest のテストで固定する。
